  Library-Wide Chat Sidebar

  The idea: A global chat panel on the Library page (not just per-project) where you can ask portfolio-level questions and manage projects from a high

  Why this is valuable: The per-project chat we built only knows about one project. But the real power questions are cross-cutting:

  - "Which projects haven't been touched in 2 weeks?"
  - "Shelve model-foundry and update the reason"
  - "What's the status of all Axiom projects?"
  - "Create a new project for the Discord bot rewrite"

  Context injection: The key difference from Kanban's per-ticket chat is that the Library chat needs full portfolio awareness. The system prompt would     
  include:
  - All project summaries (name, type, status, priority, currentGoal, lastTouched)
  - The full schema so the agent knows valid operations
  - Recent changes (last 5-10 project updates)

  This is feasible because 11-50 projects as a condensed table is well under context limits. The agent could also call the Library API to make changes     
  (shelve, promote, update goals).

  Where it sits: Right side of the Library page — same pattern as the Kanban detail panel but always available, not just when a project is selected. Toggle
   button in the header.

  My recommendation: Yes, build it. It's the "command line for your portfolio" — the thing that makes Library useful for agents and fast for you.

  ---
  Documents Section

  The idea: A file attachment/upload area within Library, separate from project records, with clean file management (rename, preview, extension tags, copy 
  path).

  Why this makes sense: Projects reference files all the time — specs, mockups, exports, PDFs, configs. Right now those are scattered. A documents section 
  gives them a home that's:
  - Browsable from the Library UI
  - Referenceable in chats (copy path → paste in chat input)
  - Organized per-project or globally
  - Agent-accessible via API

  How I'd structure it:

  $WORKSPACE_PATH/memory/projects/docs/           # global docs
  $WORKSPACE_PATH/memory/projects/docs/{slug}/    # per-project docs

  UI:
  - Separate tab or section on the Library page (not mixed with project cards)
  - Upload via drag-drop or file picker
  - File cards: icon by extension, filename (editable), size, date, extension tag badge
  - Preview panel for common types (images, text, markdown, PDF)
  - "Copy path" button on each file — copies the workspace-relative path
  - Per-project docs shown on the project detail page in a "Documents" section

  API:
  - GET /api/library/docs — list all docs (with optional ?project=slug filter)
  - POST /api/library/docs — upload (multipart/form-data)
  - PATCH /api/library/docs/[id] — rename
  - DELETE /api/library/docs/[id] — remove

  ---
  Library-Wide Chat Sidebar

  The idea: A global chat panel on the Library page (not just per-project) where you can ask portfolio-level questions and manage projects from a high     
  level.

  Why this is valuable: The per-project chat we built only knows about one project. But the real power questions are cross-cutting:
  - "What's warm that should be promoted to active?"
  - "Which projects haven't been touched in 2 weeks?"
  - "Shelve model-foundry and update the reason"
  - "What's the status of all Axiom projects?"
  - "Create a new project for the Discord bot rewrite"

  Context injection: The key difference from Kanban's per-ticket chat is that the Library chat needs full portfolio awareness. The system prompt would     
  include:
  - All project summaries (name, type, status, priority, currentGoal, lastTouched)
  - The full schema so the agent knows valid operations
  - Recent changes (last 5-10 project updates)

  This is feasible because 11-50 projects as a condensed table is well under context limits. The agent could also call the Library API to make changes     
  (shelve, promote, update goals).

  Where it sits: Right side of the Library page — same pattern as the Kanban detail panel but always available, not just when a project is selected. Toggle
   button in the header.

  My recommendation: Yes, build it. It's the "command line for your portfolio" — the thing that makes Library useful for agents and fast for you.

  ---
  Documents Section

  The idea: A file attachment/upload area within Library, separate from project records, with clean file management (rename, preview, extension tags, copy 
  path).

  Why this makes sense: Projects reference files all the time — specs, mockups, exports, PDFs, configs. Right now those are scattered. A documents section 
  gives them a home that's:
  - Browsable from the Library UI
  - Referenceable in chats (copy path → paste in chat input)
  - Organized per-project or globally
  - Agent-accessible via API

  How I'd structure it:

  $WORKSPACE_PATH/memory/projects/docs/           # global docs
  $WORKSPACE_PATH/memory/projects/docs/{slug}/    # per-project docs

  UI:
  - Separate tab or section on the Library page (not mixed with project cards)
  - Upload via drag-drop or file picker
  - File cards: icon by extension, filename (editable), size, date, extension tag badge
  - Preview panel for common types (images, text, markdown, PDF)
  - "Copy path" button on each file — copies the workspace-relative path
  - Per-project docs shown on the project detail page in a "Documents" section

  API:
  - GET /api/library/docs — list all docs (with optional ?project=slug filter)
  - POST /api/library/docs — upload (multipart/form-data)
  - PATCH /api/library/docs/[id] — rename
  - DELETE /api/library/docs/[id] — remove

  Other UI/UX Enhancements Worth Considering

  Project tracking within scope:

  1. Activity timeline on detail page — Show recent changes (status moves, field edits, chat messages) as a chronological feed. Data source: git history of
   the project file + chat timestamps.
  2. "Last touched" staleness indicator — On project cards, show a yellow/red dot if lastTouched is >7/14 days old. Makes dormant projects visually obvious
   without filtering.
  3. Quick actions on cards — Right-click or ... menu on project cards: Shelve, Archive, Open Repo, Copy Slug. Avoids navigating to detail page for common 
  operations.
  4. Batch operations — Select multiple projects (checkboxes like Kanban's bulk select), then batch-shelve, batch-tag, or batch-change-type.
  5. Project health indicators — A computed field based on: has goal? has next step? touched recently? has repo? Shows as a colored bar or score on the

● Good context from the Kanban pattern. Let me address both the chat idea and the documents idea together since they're related.

  ---
  Library-Wide Chat Sidebar

  The idea: A global chat panel on the Library page (not just per-project) where you can ask portfolio-level questions and manage projects from a high     
  level.

  Why this is valuable: The per-project chat we built only knows about one project. But the real power questions are cross-cutting:
  - "What's warm that should be promoted to active?"
  - "Which projects haven't been touched in 2 weeks?"
  - "Shelve model-foundry and update the reason"
  - "What's the status of all Axiom projects?"
  - "Create a new project for the Discord bot rewrite"

  Context injection: The key difference from Kanban's per-ticket chat is that the Library chat needs full portfolio awareness. The system prompt would     
  include:
  - All project summaries (name, type, status, priority, currentGoal, lastTouched)
  - The full schema so the agent knows valid operations
  - Recent changes (last 5-10 project updates)

  This is feasible because 11-50 projects as a condensed table is well under context limits. The agent could also call the Library API to make changes     
  (shelve, promote, update goals).

  Where it sits: Right side of the Library page — same pattern as the Kanban detail panel but always available, not just when a project is selected. Toggle
   button in the header.

  My recommendation: Yes, build it. It's the "command line for your portfolio" — the thing that makes Library useful for agents and fast for you.

  ---
  Documents Section

  The idea: A file attachment/upload area within Library, separate from project records, with clean file management (rename, preview, extension tags, copy 
  path).

  Why this makes sense: Projects reference files all the time — specs, mockups, exports, PDFs, configs. Right now those are scattered. A documents section 
  gives them a home that's:
  - Browsable from the Library UI
  - Referenceable in chats (copy path → paste in chat input)
  - Organized per-project or globally
  - Agent-accessible via API

  How I'd structure it:

  $WORKSPACE_PATH/memory/projects/docs/           # global docs
  $WORKSPACE_PATH/memory/projects/docs/{slug}/    # per-project docs

  UI:
  - Separate tab or section on the Library page (not mixed with project cards)
  - Upload via drag-drop or file picker
  - File cards: icon by extension, filename (editable), size, date, extension tag badge
  - Preview panel for common types (images, text, markdown, PDF)
  - "Copy path" button on each file — copies the workspace-relative path
  - Per-project docs shown on the project detail page in a "Documents" section

  API:
  - GET /api/library/docs — list all docs (with optional ?project=slug filter)
  - POST /api/library/docs — upload (multipart/form-data)
  - PATCH /api/library/docs/[id] — rename
  - DELETE /api/library/docs/[id] — remove

  ---
  Other UI/UX Enhancements Worth Considering

  Project tracking within scope:

  1. Activity timeline on detail page — Show recent changes (status moves, field edits, chat messages) as a chronological feed. Data source: git history of
   the project file + chat timestamps.
  2. "Last touched" staleness indicator — On project cards, show a yellow/red dot if lastTouched is >7/14 days old. Makes dormant projects visually obvious
   without filtering.
  3. Quick actions on cards — Right-click or ... menu on project cards: Shelve, Archive, Open Repo, Copy Slug. Avoids navigating to detail page for common 
  operations.
  4. Batch operations — Select multiple projects (checkboxes like Kanban's bulk select), then batch-shelve, batch-tag, or batch-change-type.
  5. Project health indicators — A computed field based on: has goal? has next step? touched recently? has repo? Shows as a colored bar or score on the    
  card. Makes it obvious which projects need attention.

  ---

  1. Library-wide chat sidebar (highest leverage — unlocks agent-driven portfolio management)
  2. Documents section (fills a real gap, clean scope)
  3. Quick actions + staleness indicators (small polish, high usability)
  4. Activity timeline (needs more data infrastructure)

● Good context from the Kanban pattern. Let me address both the chat idea and the documents idea together since they're related.

  ---
  Library-Wide Chat Sidebar

  The idea: A global chat panel on the Library page (not just per-project) where you can ask portfolio-level questions and manage projects from a high     
  level.

  Why this is valuable: The per-project chat we built only knows about one project. But the real power questions are cross-cutting:
  - "What's warm that should be promoted to active?"
  - "Which projects haven't been touched in 2 weeks?"
  - "Shelve model-foundry and update the reason"
  - "What's the status of all Axiom projects?"
  - "Create a new project for the Discord bot rewrite"

  Context injection: The key difference from Kanban's per-ticket chat is that the Library chat needs full portfolio awareness. The system prompt would     
  include:
  - All project summaries (name, type, status, priority, currentGoal, lastTouched)
  - The full schema so the agent knows valid operations
  - Recent changes (last 5-10 project updates)

  This is feasible because 11-50 projects as a condensed table is well under context limits. The agent could also call the Library API to make changes     
  (shelve, promote, update goals).

  Where it sits: Right side of the Library page — same pattern as the Kanban detail panel but always available, not just when a project is selected. Toggle
   button in the header.

  My recommendation: Yes, build it. It's the "command line for your portfolio" — the thing that makes Library useful for agents and fast for you.

  ---
  Documents Section

  The idea: A file attachment/upload area within Library, separate from project records, with clean file management (rename, preview, extension tags, copy 
  path).

  Why this makes sense: Projects reference files all the time — specs, mockups, exports, PDFs, configs. Right now those are scattered. A documents section 
  gives them a home that's:
  - Browsable from the Library UI
  - Referenceable in chats (copy path → paste in chat input)
  - Organized per-project or globally
  - Agent-accessible via API

  How I'd structure it:

  $WORKSPACE_PATH/memory/projects/docs/           # global docs
  $WORKSPACE_PATH/memory/projects/docs/{slug}/    # per-project docs

  UI:
  - Separate tab or section on the Library page (not mixed with project cards)
  - Upload via drag-drop or file picker
  - File cards: icon by extension, filename (editable), size, date, extension tag badge
  - Preview panel for common types (images, text, markdown, PDF)
  - "Copy path" button on each file — copies the workspace-relative path
  - Per-project docs shown on the project detail page in a "Documents" section

  API:
  - GET /api/library/docs — list all docs (with optional ?project=slug filter)
  - POST /api/library/docs — upload (multipart/form-data)
  - PATCH /api/library/docs/[id] — rename
  - DELETE /api/library/docs/[id] — remove

  ---
  Other UI/UX Enhancements Worth Considering

  Project tracking within scope:

  1. Activity timeline on detail page — Show recent changes (status moves, field edits, chat messages) as a chronological feed. Data source: git history of
   the project file + chat timestamps.
  2. "Last touched" staleness indicator — On project cards, show a yellow/red dot if lastTouched is >7/14 days old. Makes dormant projects visually obvious
   without filtering.
  3. Quick actions on cards — Right-click or ... menu on project cards: Shelve, Archive, Open Repo, Copy Slug. Avoids navigating to detail page for common 
  operations.
  4. Batch operations — Select multiple projects (checkboxes like Kanban's bulk select), then batch-shelve, batch-tag, or batch-change-type.
  5. Project health indicators — A computed field based on: has goal? has next step? touched recently? has repo? Shows as a colored bar or score on the    
  card. Makes it obvious which projects need attention.

  3. Quick actions + staleness indicators (small polish, high usability)
  4. Activity timeline (needs more data infrastructure)
