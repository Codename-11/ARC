## RALPLAN-DR Summary

### Principles
1. **Preserve the full current user surface while changing seams underneath** — current CLI/TUI flows include `create/use/list/import/launch/status/doctor/shared/swap/exec/shell/config/prune`, onboarding/import UI, and TUI doctor views; phases 1-4 should not regress them unless explicitly deferred (`src/cli.ts:6-220`; `src/cli.ts:331-655`; `src/tui/createProfile.ts`; `src/tui/views/DoctorView.tsx`; `tests/e2e/cli.test.ts:55-123`).
2. **Keep core truly tool-agnostic** — only config/profile/path/shared-fs/logging/lifecycle/health aggregation belong in core; tool-specific detection/import/auth/env/launch/health probing belongs in adapters (`src/config.ts:9-98`, `src/shared.ts`, `src/auth.ts:270-324`, `src/detect.ts:15-70`).
3. **Make Claude first-class without baking Claude into the core** — Claude is the first adapter target, but all current Claude quirks must move behind an adapter contract rather than remaining inside generic command services (`src/commands/profile.ts:316-333`, `src/commands/launch.ts:17-29`, `src/auth.ts:270-324`).
4. **Phase 3 and 4 must ship operator-visible value** — `arc logs`, `arc health`, and clean shutdown behavior must be real user-facing capabilities with JSON proof surfaces, not internal scaffolding only (`src/log.ts:1-38`, `src/commands/doctor.ts:27-257`, `src/tui/render.tsx:7-90`).
5. **Right-size the migration to the repo as it exists now** — use the minimum workspace/package split and compatibility shims needed to preserve root build/test/publish flows (`package.json:6-40`, `tests/e2e/cli.test.ts:7-8,47-52`, `tests/integration/profile.test.ts:34-55`).

### Decision Drivers
1. **The brief explicitly starts with monorepo + adapter work**, so the plan must satisfy real package boundaries early rather than postponing them.
2. **Current tool-specific logic is embedded in generic command/auth paths**, especially around Claude env shaping and import quirks (`src/auth.ts:270-324`, `src/commands/profile.ts:316-333`, `src/detect.ts:15-70`).
3. **Current operational surfaces are incomplete and duplicated**: logging is ad hoc, shutdown is scattered, and doctor logic is duplicated between CLI and TUI (`src/log.ts:1-38`, `src/tui/render.tsx:61-90`, `src/commands/doctor.ts:27-257`, `src/tui/views/DoctorView.tsx`).

### Viable Options

#### Option A — Full workspace split now with explicit compatibility shims (recommended)
**Approach:** Convert the repo into a pnpm workspace, move implementation into `packages/core`, `packages/adapter-claude`, and `packages/cli`, but keep the root package as the temporary publish/build/test compatibility wrapper for phases 1-4.

**Pros**
- Satisfies phase 1 honestly.
- Creates a real adapter seam before later adapter phases.
- Gives logs/lifecycle/health a shared home without another future migration.
- Keeps `dist/index.js`, root scripts, and current publish contract stable during the transition.

**Cons**
- Highest migration complexity.
- Requires compatibility handling for tests and root bundle paths.

#### Option B — Internal facades first, real packages later
**Approach:** Add `src/runtime/*` abstractions inside the single package, delay workspace/package boundaries until after phase 4.

**Pros**
- Smaller early diff.
- Lower short-term build-tool churn.

**Cons**
- Does not truly satisfy “monorepo setup” in phase 1.
- Likely causes a second migration later.
- Risks leaving Claude semantics in pseudo-generic modules.

#### Option C — Workspace shell now, defer real ownership changes
**Approach:** Add workspace config and empty packages but leave most code in root `src/` until later phases.

**Pros**
- Fastest initial setup.
- Lowest immediate breakage risk.

**Cons**
- Mostly scaffolding.
- Weakens phase 2 because the adapter boundary is not real.
- Encourages logs/health/shutdown to land on legacy code paths.

### Recommendation
Choose **Option A** with a minimal three-package split and explicit compatibility rules:
- **Root package remains the publishable `@axiom-labs/arc-cli` wrapper for phases 1-4.** It keeps root scripts, root `dist/index.js`, and root developer commands stable while delegating implementation to workspace packages.
- **`packages/core`** owns only tool-agnostic primitives: config, profile repository, path/fs helpers, shared-layer primitives, structured logging, lifecycle registry, health aggregation.
- **`packages/adapter-claude`** owns all Claude-specific behavior: detection, import quirks, OAuth parsing, env shaping, install hints, launch prep, tool-specific health probes, tool-specific profile artifacts.
- **`packages/cli`** owns Commander/TUI presentation plus composition across core + adapters.

## Acceptance Criteria
1. **Workspace migration:** the repo becomes a pnpm workspace, yet root `pnpm build`, `pnpm typecheck`, `pnpm test`, and the root `arc` bin / `dist/index.js` flow still work.
2. **Core migration:** generic config/profile/path/shared/log/lifecycle/health aggregation code is owned by `packages/core`, and tool-specific logic is not newly introduced there.
3. **Claude adapter parity:** detection, import, OAuth parsing, env shaping, install hints, launch prep, and health probes for Claude route through an adapter contract without regressing current behavior.
4. **CLI/TUI unification:** CLI and TUI create/import/onboarding/doctor flows consume the same adapter-backed service layer for tool-specific behavior.
5. **Logging:** structured log events are emitted for command execution, profile mutations, launch lifecycle, health checks, and shutdown paths; `arc logs` supports limit/filter/json output.
6. **Shutdown:** signal-driven exits and child-process exits normalize through a shared lifecycle system for the in-scope interactive/session paths (`launch`, `exec`, `shell`, TUI teardown, CLI boundary), restore the terminal when needed, and log the outcome.
7. **Health:** `arc health` provides fast runtime readiness checks with JSON output, while `doctor` remains the broader install/remediation surface built on shared health primitives.
8. **Verification:** existing tests continue to pass, and new characterization/integration/E2E coverage proves adapter parity, logs, health, and shutdown behavior.

## Risks and Mitigations
- **Risk:** Workspace migration breaks root publish/build/test contract.
  - **Mitigation:** explicitly keep root as the temporary compatibility wrapper and validate `dist/index.js` continuously (`package.json:6-40`, `tests/e2e/cli.test.ts:47-52`).
- **Risk:** Claude logic accidentally fossilizes inside core during the migration.
  - **Mitigation:** treat any new Claude-specific env/import/detect logic inside core as a blocker; adapter owns it.
- **Risk:** CLI and TUI drift because only CLI is migrated to adapter-backed services.
  - **Mitigation:** phase 2 includes both CLI and TUI call sites as required scope.
- **Risk:** Lifecycle centralization fails because commands still exit directly.
  - **Mitigation:** add the CLI-boundary exit/result adapter before or during lifecycle rollout.
- **Risk:** `doctor` and `health` duplicate each other.
  - **Mitigation:** define `health` narrowly as runtime readiness and make both surfaces presenters over shared health primitives.

## Pre-mortem (Deliberate Mode)
1. **The workspace migration lands, but the root package contract quietly breaks.**
   - Leading indicator: `dist/index.js` or root scripts stop matching E2E assumptions.
   - Prevention: keep a documented root-wrapper contract and verify it in every migration step.
2. **The adapter seam exists on paper, but Claude logic remains spread across CLI/TUI/core.**
   - Leading indicator: `packages/core` or multiple presenters still own `CLAUDE_*` env rules or `.claude.json` quirks.
   - Prevention: make adapter-backed CLI + TUI integration part of phase 2 acceptance, not optional follow-up.
3. **Shutdown behavior becomes less predictable after centralization.**
   - Leading indicator: double exits, hanging child processes, or corrupted terminal state after Ctrl+C.
   - Prevention: preserve current presenter cleanup behavior and add signal-focused regression tests plus structured shutdown logs.

## ADR
- **Decision:** Implement phases 1-4 by converting ARC into a minimal workspace with `core`, `adapter-claude`, and `cli`, while preserving the root package as a temporary compatibility wrapper and keeping all tool-specific behavior inside the Claude adapter rather than core.
- **Drivers:**
  1. The brief requires monorepo + adapter work first.
  2. Current generic modules still contain Claude-specific behavior.
  3. Logging/lifecycle/health need shared primitives to avoid more duplication.
- **Alternatives considered:**
  - internal facades only in a single package
  - workspace shell without real ownership changes
- **Why chosen:** it is the smallest structure that honestly satisfies phases 1-4 while minimizing future rework.
- **Consequences:**
  - migration complexity rises in the short term
  - compatibility shims may temporarily increase file count
  - future adapters and later observability phases become substantially easier
- **Follow-ups:**
  - phase 5 can add Codex/Gemini adapters against the same contract
  - later phases can build on core logging/lifecycle events without another structural cut
